# NATS JetStream cluster

Three NATS 2.15 servers with JetStream, TLS everywhere, least-privilege accounts, health checks,
metrics in the existing LGTM stack, idempotent stream provisioning, backups with restore drills, and
rolling upgrades.

> [!IMPORTANT]
> **This is a three-container cluster on ONE Docker host.** It provides quorum (any one of the three
> servers can fail), R3 replication, and zero-downtime rolling restarts. It does **not** provide
> host-level high availability: the host, its kernel, its disk, and the Docker daemon are single points
> of failure. When the host dies, the whole cluster dies with it. See
> [Single host vs. production](#3-single-host-vs-production) and [Moving to multi-host production](#16-moving-to-a-real-multi-host-production-deployment).

## 1. Architecture

```text
 host 127.0.0.1:4222/4223/4224 (TLS) ─────────┐
                                              ▼
 shared_network (external, shared by all stacks)
 ├─ apps in other stacks ── tls://nats-N:4222 ─►  nats-1   nats-2   nats-3      client port only
 ├─ Alloy (LGTM) ───────── http://nats-N-exporter:7777/metrics
 └─ nats-box, backup-sync (on demand: profile "tools")

 nats_cluster (private, internal: no egress, nothing published, no other stacks)
 ├─ nats-1-cluster:6222 ◄─ mutual TLS routes ─► nats-2-cluster:6222 ◄─► nats-3-cluster:6222
 └─ nats-N-exporter ── http://nats-N-cluster:8222 (monitoring: plain HTTP, never on shared_network)

 volumes: nats_jetstream_1 / _2 / _3  (one per server, never shared)
```

| Service | Image (pinned by tag and digest) | Networks | Purpose |
|---|---|---|---|
| `nats-1`, `nats-2`, `nats-3` | `nats:2.15.2-alpine3.22` | shared, cluster | JetStream servers. Client port 4222 on both networks; routes 6222 and monitoring 8222 bound to the cluster address only. |
| `nats-N-init` | same | none | One-shot job: chowns the server's named volume to the non-root UID. |
| `nats-N-exporter` | `natsio/prometheus-nats-exporter:0.20.3` | shared, cluster | Converts one server's monitoring endpoint into Prometheus metrics on :7777. |
| `nats-box` (profile `tools`) | `natsio/nats-box:0.20.2` (nats CLI 0.5.1) | shared | Operator CLI used by `scripts/*.sh`, connects like an app. |
| `backup-sync` (profile `tools`) | `rclone/rclone:1.75.2` | shared | Optional off-host copy of backups. |

The alpine variant of the NATS image is used deliberately: the `scratch` image has no shell or
`wget`, so it cannot run an in-container health check. All images are multi-arch (amd64 and arm64).

## 2. Dependencies: required, optional, unnecessary

NATS JetStream is self-contained. Servers find each other through the routes in their config. Agreement
on streams, consumers, and placement comes from NATS's built-in Raft groups (one meta group plus one
group per stream and per consumer). Data lives in each server's own `store_dir`
([JetStream clustering](https://docs.nats.io/running-a-nats-service/configuration/clustering/jetstream_clustering),
[Clustering & replication](https://docs.nats.io/learn/clustering)).

| Component | Status | Why |
|---|---|---|
| Local persistent disk per server (Docker named volume) | **Required** | NATS docs: store JetStream data "locally on a fast SSD", "specifically avoid NAS or NFS storage", and "each JetStream enabled server MUST use its own individual storage directory" ([NATS configuration docs](https://github.com/nats-io/nats.docs/blob/master/running-a-nats-service/configuration/README.md)). |
| TLS certificates (private CA) | **Required** (security requirement of this stack) | Generated by `scripts/pki.sh`, or provided by your PKI. |
| Prometheus-compatible metrics backend + Grafana | Optional | Reuses LGTM (Alloy → Mimir → Grafana). Nothing new is deployed. |
| Object storage (SeaweedFS / MinIO / any S3) | Optional, **backups only** | Backups are plain directories, so any rclone remote works. S3 cannot be live JetStream storage: the filestore needs a local POSIX filesystem, and NATS 2.15 has no object-storage backend. |
| PostgreSQL / PgBouncer, Valkey, DragonflyDB, Kafka, ClickHouse, ZooKeeper/etcd | **Unnecessary** | No external database, cache, broker, or coordination service. NATS uses its own Raft consensus. |

## 3. Single host vs. production

| | This stack (3 containers, 1 host) | Real production (3 hosts in separate failure domains) |
|---|---|---|
| Survives one server process crash, OOM kill, or bad upgrade | Yes | Yes |
| Survives loss of the host, kernel panic, Docker daemon restart | **No**: total outage | Yes (one host) |
| Survives disk failure | **No**: all three volumes share one disk | Yes (one disk) |
| Survives power loss without losing acknowledged writes | Only because `sync_interval: always` (see §9) | Yes with replication alone; `always` adds protection against correlated failures |
| Rolling restarts and upgrades without downtime | Yes | Yes |
| Capacity (CPU, RAM, disk I/O) | Shared by all three servers | Independent |

Use this stack for staging, development, and single-server production where a host outage is an
accepted risk. For anything that must survive a host failure, see §16.

## 4. Prerequisites

- **Docker Engine 25 or newer with the Compose v2 plugin.** The health check uses `start_interval`.
  Tested with Engine 29.9.2 and Compose v5.7.0 on amd64; all images are also published for arm64,
  including Apple Silicon.
- `openssl` (the LibreSSL that ships with macOS works, as does OpenSSL 1.1/3.x) and `bash` 3.2 or newer.
- The shared network, as for every stack in this repository:

  ```bash
  docker network create shared_network
  ```

  > If the network already exists, Docker will return an error that can be safely ignored.

- **Disk:** at least 3 × `NATS_JS_MAX_FILE` (30 GiB by default) plus about 20% free space on the disk
  holding Docker's volumes. On Docker Desktop, check *Settings → Resources → Disk usage limit*: the
  other stacks share the same disk.
- Run the scripts as the **non-root user** who operates the stack. The containers run with that
  user's UID so they can read its 0600 secret files without extra capabilities.
- **Docker Desktop for Mac:** its file sharing (VirtioFS) can present bind-mounted files as
  root-owned ([docker/for-mac#6243](https://github.com/docker/for-mac/issues/6243)).
  `setup.sh` probes whether a container running as your UID can read the secrets and write
  `backups/`. If it cannot, setup falls back to `NATS_UID=0`/`NATS_GID=0` and tells you so. The
  containers still run with every capability dropped, a read-only root filesystem, and
  `no-new-privileges`.

## 5. Quick start

```bash
cd NATS
./scripts/setup.sh                 # .env (UID/GID), CA + node certificates, passwords + bcrypt hashes
docker compose up -d               # 3 servers, 3 exporters (init jobs run first)
./scripts/check-cluster.sh         # liveness, quorum, readiness, replicas -> exit 0
./scripts/provision-jetstream.sh   # idempotent: ORDERS stream (R3) + durable consumer
./scripts/validate.sh              # end-to-end test on a temporary R3 stream (non-disruptive)

# Metrics and alerts in the LGTM stack (see section 12)
curl -X POST http://localhost:3400/-/reload   # Alloy reloads config.alloy with the NATS scrape block
./scripts/load-alert-rules.sh                 # alert rules into the Mimir ruler (namespace "nats")
```

The operator CLI uses one of the stack identities, and passwords never appear on the command line:

```bash
docker compose run --rm nats-box sys-admin server list
docker compose run --rm nats-box sys-admin server report jetstream
docker compose run --rm nats-box app-admin stream ls
docker compose run --rm nats-box app-admin stream info ORDERS
```

## 7. Networking and client URLs

| Client location | URLs | TLS name verified |
|---|---|---|
| Container on `shared_network` (other stacks) | `tls://nats-1:4222,tls://nats-2:4222,tls://nats-3:4222` | `nats-1`, `nats-2`, `nats-3` (in the certificates) |
| Process on the Docker host | `tls://localhost:4222,tls://localhost:4223,tls://localhost:4224` | `localhost` / `127.0.0.1` (in the certificates) |
| Remote host (opt-in) | `tls://<host-dns>:4222,tls://<host-dns>:4223,tls://<host-dns>:4224` | `<host-dns>`; add it via `NATS_TLS_EXTRA_SANS` |

Enabling remote clients:

1. Set `NATS_CLIENT_BIND=0.0.0.0` (or one interface IP) in `.env`.
2. Set `NATS_TLS_EXTRA_SANS=DNS:nats.example.com,IP:192.0.2.10`.
3. Run `scripts/pki.sh`, which re-issues the certificates because the SANs changed.
4. Run `docker compose up -d`. The port mapping is not reloadable, so use `scripts/rolling-restart.sh` to keep the cluster available.
5. Allow 4222–4224 in the host firewall only from the networks that need it.

**Discovery and advertised addresses.** NATS servers normally gossip their client URLs, and clients
add them to their server list. Here those would be container IPs, which host and remote clients cannot
reach and which TLS cannot verify against the certificate names. `cluster.no_advertise: true` turns
this off ([cluster config](https://docs.nats.io/reference/config/cluster/)). As a result, **every
client must be configured with all three URLs**, and adding a server means updating client configs.
`cluster.advertise` is set to each server's `nats-N-cluster:6222` name, so route TLS verifies a
stable hostname rather than an IP.

**Why a separate private network for routes and monitoring.** On `shared_network`, any container from
any stack could reach the route port and the unauthenticated monitoring endpoint, which exposes server,
connection, and account details. Both now bind only to each server's alias on the `internal`
`nats_cluster` network. Only the three servers and their exporters are attached to it, it has no
egress, and Docker cannot publish ports from it. Verified: from `shared_network`, ports 6222 and 8222
are closed and 4222 is open. Routes additionally use mutual TLS with
`verify_cert_and_check_known_urls`, so a certificate from the same CA without a route SAN cannot join
the cluster. The cost: each exporter needs both networks.

## 8. Security: TLS, authentication, secrets

### TLS and certificate provisioning

`scripts/pki.sh` (run by `setup.sh`) creates:

- a private ECDSA P-256 CA (`certs/ca/ca.key`, `certs/ca/ca.crt`, 10 years);
- one key and certificate per server (397 days by default, `NATS_TLS_LEAF_DAYS`), with EKU
  `serverAuth, clientAuth`. Route TLS uses the same certificate as both client and server certificate
  ([TLS config](https://docs.nats.io/reference/config/tls/)). SANs are `nats-N`, `nats-N-cluster`,
  `localhost`, `127.0.0.1`, `::1`, plus `NATS_TLS_EXTRA_SANS`.

Clients and servers require TLS 1.2 or newer (TLS 1.3 is negotiated in practice). Clients must trust
`certs/ca/ca.crt`, which is public: distribute it to applications.

| Task | Command |
|---|---|
| Renew all node certificates (new keys) | `scripts/pki.sh --renew && docker compose kill -s SIGHUP nats-1 nats-2 nats-3` |
| Check expiry | `openssl x509 -noout -enddate -in certs/nats-1/server.crt`, or `nats server check server --tls-cert-warn 720h` |
| Use your own PKI (Vault, step-ca, corporate CA) | Put PEM files at the same paths with the same SANs and EKUs, then reload. |

Certificate reload is non-disruptive: new connections get the new certificate, and existing ones keep
their session. This was verified, see §17. The scripts rewrite files in place, keeping the inode, so
the bind-mounted Compose secrets see the new content. If a tool replaces files by renaming them, as
cert-manager and Vault Agent do, recreate the containers with `scripts/rolling-restart.sh` instead of
sending SIGHUP.

**Rotating the CA:**

1. Create the new CA.
2. Put old and new CA certificates in `certs/ca/ca.crt`, distribute that bundle to clients, and reload.
3. Re-issue the node certificates from the new CA, then reload.
4. When every client trusts the new CA, remove the old one from the bundle and reload.

`certs/ca/ca.key` is only needed to issue certificates. In production, keep it offline or in your PKI,
not on the NATS host.

Optional client mTLS: set `verify: true` in the top-level `tls {}` block and issue client certificates
from the CA. Every client must then present one.

### Authentication and authorization

`config/accounts.conf` defines no `no_auth_user`, so anonymous connections are impossible. Every user is
limited to `allowed_connection_types: ["STANDARD"]`.

| Account | User | May | May not |
|---|---|---|---|
| `SYS` (system account) | `sys-admin` | Server and cluster administration: `server list/report/check`, `peer-remove`, `rescue` | Application data. Operators only. |
| `APP` | `app-admin` | JetStream administration in `APP`: create, edit, and delete streams and consumers; backup and restore | Anything in `SYS` |
| `APP` | `orders-publisher` | Publish `orders.>`; receive PubAcks on `_INBOX_orders_publisher.>` | JetStream API, other subjects, other users' inboxes |
| `APP` | `orders-consumer` | `CONSUMER.INFO` and `CONSUMER.MSG.NEXT` of `ORDERS > order-processor`; ack its messages; receive on `_INBOX_orders_consumer.>` | Create, edit, or delete anything; read raw subjects; other consumers |

Notes:

- **Inbox prefixes.** With the default `_INBOX.>`, any user in the account could subscribe to every
  reply, including messages pulled by other consumers. Each restricted user therefore gets its own
  prefix, and the client must set it (§10).
- **Forward compatible ack permissions.** Both v1 (`$JS.ACK.ORDERS.order-processor.>`) and v2
  (`$JS.ACK.*.*.ORDERS.order-processor.>`) ack subjects are allowed. NATS 2.15 uses v1, and 2.16 makes
  v2 the default ([2.14 upgrade notes](https://docs.nats.io/release-notes/upgrade-to-2.14),
  [2.15 upgrade notes](https://docs.nats.io/release-notes/upgrade-to-2.15)).
- **Admin isolation.** Admin credentials are used only by the on-demand `nats-box` container and are
  never handed to applications. The monitoring endpoint is unauthenticated, but it is only reachable
  from the private cluster network.
- **Verified.** The publisher's JetStream publish succeeds, and its attempts at `billing.created`,
  `$JS.API.STREAM.LIST`, and subscribing to `orders.>` are rejected. The consumer can fetch and ack, but
  cannot create consumers or read stream info. The server logs show violations only for the forbidden
  operations.

**Adding an application user:**

1. Add the user to `config/accounts.conf` with the narrowest permissions (copy the `orders-*` pattern).
2. Add the name to `NATS_USERS` in `scripts/credentials.sh`.
3. Run `scripts/credentials.sh`.
4. Reload with `docker compose kill -s SIGHUP nats-1 nats-2 nats-3`.
5. Give `secrets/users/<user>.password` and `certs/ca/ca.crt` to the application.

With many teams or tenants, move to decentralized JWT auth (`nsc`, operator mode) or NKEYs. Both remove
password hashes from the server side
([authorization](https://docs.nats.io/learn/security/authorization), [accounts](https://docs.nats.io/reference/config/accounts/)).

### Secret handling

- Nothing secret is committed. `.gitignore` excludes `.env`, `certs/`, `secrets/`, and `backups/`, and
  the tracked configs reference secrets only by path or variable.
- Passwords are 256-bit random (64 hex characters, no trailing newline), stored in `0600` files inside
  `0700` directories. Servers only see bcrypt hashes (cost 11) in `secrets/server/credentials.conf`,
  which `accounts.conf` includes as variables.
- Secrets reach containers as Compose `secrets` (read-only bind mounts). They are never passed as
  environment variables or command-line arguments, so they do not show up in `docker inspect`, `ps`, or
  shell history. Hashing happens in a network-less container, with the passwords piped over stdin.
- **Rotation:** run `scripts/credentials.sh --rotate <user>` (or `--rotate-all`), then
  `docker compose kill -s SIGHUP nats-1 nats-2 nats-3`. Verified: the new password works immediately and
  the old one is rejected (*Authorization Violation*). Then update the application's copy.
- Applications should mount their password and the CA file as their own Compose secret. Never put the
  password into a URL that ends up in logs.
- Back up `certs/` and `secrets/` encrypted and separately from the message backups (§14).

### Container hardening

- Servers run as the operator's UID (from `.env`), not root. The only exception is the Docker
  Desktop fallback described in §4.
- Root filesystems are read-only.
- `cap_drop: [ALL]` and `no-new-privileges` apply to every container.
- `tmpfs` is used for `/tmp`.
- `ulimits` and CPU and memory limits are set.
- The only privileged step is the one-shot `nats-N-init` job: `CHOWN`, `FOWNER`, and `DAC_OVERRIDE`,
  no network, just `chown` of its own volume.

## 9. JetStream: replication, limits, durability

### Clustering does not replicate streams by itself

A stream's replica count comes from its own `num_replicas`, which **defaults to 1**. An R1 stream on a
three-node cluster lives on a single server and goes down with it. Every stream that matters must ask
for 3 replicas explicitly ([JetStream clustering](https://docs.nats.io/running-a-nats-service/configuration/clustering/jetstream_clustering),
[Surviving node loss](https://docs.nats.io/learn/jetstream/surviving-node-loss)).
`scripts/provision-jetstream.sh` verifies this after every run: each declared stream and consumer must
report N distinct current peers, or the script fails.

### Idempotent provisioning

`jetstream/streams/*.json` and `jetstream/consumers/<STREAM>/*.json` hold JetStream API configs.
Durations are in nanoseconds. The script reconciles them through `nats stream|consumer add|edit --config`.

| Situation | Result (verified) |
|---|---|
| Asset missing | Created |
| Exists, same config | No-op; safe to re-run any time |
| Exists, changed mutable field (e.g. `max_age`, `max_ack_pending`) | Edited in place |
| Changed immutable field (e.g. `storage`) | Fails loudly: *stream configuration update can not change storage type (10052)* |

The example `ORDERS` stream is R3 file storage, with limits retention, `discard: old`, a 7-day
`max_age`, 1 GiB `max_bytes`, a 2-minute duplicate window, and `deny_delete`.

The `order-processor` consumer is a durable pull consumer:

- explicit acks;
- `ack_wait` of 30 s, equal to `backoff[0]`, because the server normalises `ack_wait` to the first
  backoff value;
- backoff of 30 s, 1 m, 2 m, 5 m, 10 m;
- `max_deliver` of 10.

`num_replicas: 0` means the consumer inherits the stream's R3. This was deliberate: the restore drill
showed that an explicit `num_replicas: 3` makes a backup impossible to restore with fewer replicas.

### Limits and sizing (assumptions, measure before production)

| Layer | Setting | Default here |
|---|---|---|
| Container | `NATS_CPUS`, `NATS_MEMORY_LIMIT`, `NATS_GOMEMLIMIT` (~80% of the limit), `NATS_NOFILE` | 2 CPUs, 2 GiB, 1600 MiB, 65536 |
| Server | `max_memory_store` / `max_file_store` (`NATS_JS_MAX_MEMORY` / `NATS_JS_MAX_FILE`) | 512 MB / 10 GB per server |
| Server | `max_connections`, `max_payload`, `max_pending`, `write_deadline` | 10,000, 1 MB, 64 MB, 10 s |
| Account `APP` | `max_memory`, `max_file`, `max_streams`, `max_consumers` (per stream), `max_bytes_required` | 512 MB, 24 GB, 100, 1000, true |
| Stream | `max_bytes`, `max_age`, `max_msg_size`, `max_consumers` | 1 GiB, 7 d, 1 MiB, 100 |

The workload assumption behind these numbers is a few thousand messages per second of ≤1 KiB, up to
about 1,000 connections, and up to 100 streams.

How the limits interact:

- **R3 multiplies account usage.** Account limits count replicas × bytes, so a 1 GiB R3 stream uses
  3 GiB of `max_file` ([sizing](https://docs.nats.io/learn/deployment/sizing-and-resources)).
- **Pin the defaults.** NATS defaults (75% of host RAM and disk) are wrong when three servers share one
  disk, so both are set explicitly.
- **`max_bytes` is mandatory.** `max_bytes_required` stops any stream from being created without a
  size limit.
- **Consumer limit.** NATS 2.15 limits streams to 1000 consumers by default (`default_max_consumers`).
- **CPU and GC.** Go ≥ 1.25 sizes `GOMAXPROCS` from the CPU limit, and `GOMEMLIMIT` keeps the GC ahead
  of the cgroup OOM killer.

### Durability: `sync_interval: always`

By default JetStream fsyncs every 2 minutes and relies on replicas in *independent* failure domains to
survive an OS crash. A PubAck means a quorum holds the write, not that it is on disk
([Replication and R3](https://docs.nats.io/learn/clustering/replication-and-r3)). On a single host all
three replicas share one kernel, page cache, and disk, so a power loss could drop up to 2 minutes of
writes that were already acknowledged. This stack therefore sets `sync_interval: always`, which syncs
before the PubAck. NATS 2.15 batches these syncs for replicated streams, which makes the setting
affordable ([2.15 release](https://nats.io/blog/nats-server-2.15-release/)).

Measured in the validation sandbox (R3 file stream, 1 KiB messages; relative numbers only, your disk
will differ):

| `sync_interval` | async publish (batched acks) | sync publish (one ack per message) |
|---|---|---|
| `always` (this stack) | 27,586 msg/s | 687 msg/s, avg 1.45 ms |
| `2m` (upstream default) | 29,353 msg/s | 2,105 msg/s, avg 0.47 ms |

Changing it requires a rolling restart, not a reload. On a multi-host cluster with replicas in separate
failure domains, `2m` is a reasonable choice again.

### Quorum: what each failure costs

| Servers up | Meta group (create/edit streams) | R3 stream writes | R3 consumers | Health |
|---|---|---|---|---|
| 3 of 3 | ✔ | ✔ | ✔ | OK |
| 2 of 3 | ✔ | ✔ (after a re-election if the leader was lost: about 1 s graceful, about 5 s on a crash, measured) | ✔ | Degraded: tolerates **no** further failure |
| 1 of 3 | ✘ no leader | ✘ publishes time out | ✘ stall | Critical. Data is intact and nothing is lost; service resumes when a second server returns. |

## 10. Client examples and reconnection behaviour

Applications need three things: all three URLs, the CA file, and their own user and password, plus
the user's **inbox prefix** if it has one.

**Go** (nats.go v1.55, `jetstream` package). This publisher and consumer pair was run against the
cluster while a server was killed (§17):

```go
pw, _ := os.ReadFile("/run/secrets/nats_password") // e.g. a Compose secret in your app stack
nc, err := nats.Connect(
    "tls://nats-1:4222,tls://nats-2:4222,tls://nats-3:4222",
    nats.Name("orders-api"),
    nats.UserInfo("orders-publisher", strings.TrimSpace(string(pw))),
    nats.RootCAs("/run/secrets/nats_ca.crt"),
    nats.CustomInboxPrefix("_INBOX_orders_publisher"), // required by the permissions
    nats.RetryOnFailedConnect(true), // start even if NATS is not up yet (independent stacks)
    nats.MaxReconnects(-1),          // never give up (default: 60 attempts)
    nats.ReconnectWait(time.Second),
)
js, _ := jetstream.New(nc)

// Publish with a deduplication id; retry until acked. The stream's 2-minute
// duplicate window makes retries safe: no duplicates after failover.
id := orderID
for {
    ctx, cancel := context.WithTimeout(context.Background(), 2*time.Second)
    _, err := js.Publish(ctx, "orders.created", payload, jetstream.WithMsgID(id))
    cancel()
    if err == nil {
        break
    }
    time.Sleep(250 * time.Millisecond) // timeout / no responders during a leader election
}

// Worker (user orders-consumer, inbox prefix _INBOX_orders_consumer):
cons, _ := js.Consumer(ctx, "ORDERS", "order-processor") // needs CONSUMER.INFO only
cc, _ := cons.Consume(func(m jetstream.Msg) {
    if err := handle(m.Data()); err != nil {
        m.Nak() // redelivered according to the consumer's backoff
        return
    }
    m.Ack()
})
defer cc.Stop()
```

**nats CLI from the host.** The password comes from a file and never from the command line:

```bash
NATS_PASSWORD="$(cat secrets/users/orders-publisher.password)" nats \
  --server tls://localhost:4222,tls://localhost:4223,tls://localhost:4224 \
  --tlsca certs/ca/ca.crt --user orders-publisher --inbox-prefix _INBOX_orders_publisher \
  pub --jetstream orders.created '{"id":1}'
```

Inbox prefix option in other official clients:

| Client | Option |
|---|---|
| nats.js | `inboxPrefix` |
| nats.py | `inbox_prefix` |
| jnats | `Options.Builder.inboxPrefix()` |
| NATS.Net | `NatsOpts.InboxPrefix` |

**Reconnection behaviour (measured).** A stream leader was killed with SIGKILL while 3,000 messages
were being published and consumed:

- The consumer connection reconnected to another server immediately.
- Publishing paused for about 5.3 s during the stream leader election. The client saw timeouts and
  *no response from stream*, retried 5 times with the same `Nats-Msg-Id`, and the stream ended with
  exactly 3,000 messages: 0 lost, 0 duplicates.

With a graceful stop (lame duck mode), leadership moves first and the pause is about 1 s.

nats.go defaults: 60 reconnect attempts, 2 s apart, with an 8 MB reconnect buffer for **core** NATS
publishes ([nats.go](https://pkg.go.dev/github.com/nats-io/nats.go)). JetStream publishes are
request/reply, so they are not buffered: retry them yourself with a Msg-Id, as above. Durable consumers
resume from the ack floor, and messages that were not acked are redelivered after `ack_wait`/backoff.

## 11. Health checks

| Level | Endpoint (monitoring port, private network) | Fails when | Used by |
|---|---|---|---|
| **Liveness** (process + JetStream enabled) | `/healthz?js-enabled-only=true` | Process hung or JetStream failed to start | Docker `healthcheck` (busybox `wget` in the alpine image) |
| **Quorum** (meta group) | `/healthz?js-meta-only=true` | This server has no meta leader or is not current with it | `check-cluster.sh` |
| **Readiness** | `/healthz` | Quorum check fails, or any stream or consumer replica on this server is not current (catching up, filestore I/O error) | `check-cluster.sh`, `rolling-restart.sh`, exporter → alerts |

The Docker health check deliberately ignores peers. Verified on 2.15.2 with two of three servers
stopped:

- The survivor's `js-enabled-only` returned 200, so the container stayed *healthy*.
- `js-meta-only` and `/healthz` returned 503: *JetStream has not established contact with a meta leader*.
- `js-server-only` also returned 200, so it is **not** a quorum signal.

With one server down, both survivors stayed fully ready. After restarting the stopped servers, all three
were ready again within about 7 s.

`scripts/check-cluster.sh` combines per-node probes with `nats server check meta|jetstream|stream|consumer`:

```text
node     container  liveness  quorum  ready   routes-to
nats-1   running    ok        ok      ok      nats-2
nats-2   running    ok        ok      ok      nats-1
nats-3   exited     -         -       -       -
meta group: CRITICAL JetStream Meta Cluster Crit:1 offline | peers=3;3;3 peer_offline=1 ...
stream ORDERS (R3): CRITICAL ORDERS Crit:1 replicas offline OK:3 peers ...
RESULT: DEGRADED - quorum intact (2/3 servers live) but redundancy is reduced; see lines above
```

Exit codes: `0` healthy, `1` degraded (quorum intact), `2` critical (no quorum). `--quiet` prints only
the result line, for cron or CI.

**Other stacks and readiness.** Compose `depends_on` only works inside one project, so an application
stack cannot depend on `nats-1`. Applications should instead:

- connect with `RetryOnFailedConnect` and unlimited reconnects;
- treat JetStream as ready once a cheap API call succeeds, such as `js.Stream(ctx, "ORDERS")` or
  `CONSUMER.INFO` for restricted users;
- expose their own readiness only after that.

## 12. Monitoring and alerting

**Stack choice: LGTM, not Prometheus-Grafana.**

- `LGTM/` is the actively developed stack: Mimir is the default Grafana datasource, Grafana has SSO and
  a domain, and the recent commits are there.
- Both stacks define `container_name: grafana`, so they cannot run side by side.
- LGTM already has Alloy (collector), Mimir (long-term storage on SeaweedFS), and Grafana with
  file-provisioned dashboards. Nothing is duplicated: Alloy gets one scrape block, and Grafana gets one
  dashboard file.

| Piece | Where | Applied by |
|---|---|---|
| Scrape `nats-{1,2,3}-exporter:7777` (job `nats`) → Mimir `remote_write` | Block appended to `LGTM/config/config.alloy` (copy in `monitoring/alloy-nats.alloy`) | `curl -X POST http://localhost:3400/-/reload` (no restart) |
| Dashboard *NATS JetStream cluster* (folder LGTM) | `LGTM/config/grafana/provisioning/dashboards/json/nats-jetstream.json` | Grafana picks up provisioned files automatically |
| Alert rules (namespace `nats`) | `monitoring/nats-alerts.yml` | `scripts/load-alert-rules.sh` runs `mimirtool rules check`, then `promtool test rules`, then a sync limited to the `nats` namespace |

If you use `Prometheus-Grafana/` instead, add this to its `prometheus.yml` and attach
`nats-alerts.yml` as a rule file:

```yaml
  - job_name: nats
    static_configs:
      - targets: ['nats-1-exporter:7777', 'nats-2-exporter:7777', 'nats-3-exporter:7777']
```

**Exporter caveat (verified).** While a server is unreachable, its exporter keeps serving the
**last** `gnatsd_varz_*` values. The rules therefore detect liveness only through
`gnatsd_healthz_status` and `gnatsd_healthz_status_value{value="unreachable"}`.

| Alert | Severity | Fires when |
|---|---|---|
| `NatsJetStreamQuorumLost` | critical | Fewer than 2 servers pass `/healthz` (also when no NATS metrics arrive at all) |
| `NatsJetStreamDisabled` | critical | JetStream turned itself off on a server |
| `NatsServerDown` | warning | An exporter cannot reach its server |
| `NatsServerNotReady` | warning | A server runs but `/healthz` fails for 2 m |
| `NatsMetricsScrapeFailing` | warning | Alloy cannot scrape an exporter |
| `NatsStreamReplicaUnavailable` | warning | An R3 stream is reported by fewer than 3 servers for 5 m |
| `NatsStreamReplicaLagging` | warning | Replicas more than 1,000 messages apart for 5 m |
| `NatsJetStreamFileStorageHigh` / `...Critical` | warning / critical | File store at 75% / 90% of `max_file_store` |
| `NatsJetStreamMemoryStorageHigh` | warning | Memory store at 80% of `max_memory_store` |
| `NatsJetStreamReservationsHigh` | warning | Streams' `max_bytes` reservations at 90% of `max_file_store` |
| `NatsAccountStorageHigh` | warning | Account at 80% of `max_file` |
| `NatsStreamNearByteLimit` | info | Stream at 90% of `max_bytes` (oldest data is being dropped) |
| `NatsProcessMemoryHigh` | warning | RSS at 90% of `GOMEMLIMIT` |
| `NatsCPUHigh` | warning | CPU above 80% of the allowed cores for 15 m |
| `NatsConnectionsHigh` | warning | Connections at 80% of `max_connections` |
| `NatsSlowConsumers` | warning | New slow consumers (core NATS drops) |
| `NatsDiskIOSaturated` | warning | JetStream I/O operations waiting for disk slots |
| `NatsConsumerBacklogHigh` / `NatsConsumerRedeliveriesHigh` | warning | Consumer backlog over 10k, or more than 100 messages in redelivery |

**Notifications.** Mimir in `-target=all` mode runs the ruler but not the Alertmanager. Running Mimir
2.17.11 with `-modules` shows `ruler (in: all, backend)` and `alertmanager (in: backend)`. Alerts
evaluate and show in Grafana under *Alerting → Alert rules → Data source-managed*. To get
notifications, add `alertmanager` to Mimir's `-target` (its storage is already configured in
`mimir.yml`), or point `ruler.alertmanager_url` at an Alertmanager.

**Not covered: host disk and container metrics.** The LGTM stack has no node-exporter or cAdvisor.
Add them to alert on free space of Docker's disk, which matters because `max_file_store` assumes that
space exists.

**Logs.** NATS logs to stdout. The Docker `json-file` driver rotates them at 5 × 20 MB per container.
Shipping them to Loki would need Alloy's `loki.source.docker` with the Docker socket mounted into Alloy;
that is not enabled here.

## 13. Operations

### Start, stop, reload

| Action | Command / behaviour |
|---|---|
| Start | `docker compose up -d` |
| Stop | `docker compose stop`. SIGUSR2 starts lame duck mode: Raft leadership moves, new connections are refused, and existing ones are closed over up to 30 s after a 10 s grace period ([rolling upgrades](https://docs.nats.io/learn/deployment/rolling-upgrades)). It takes about 1 s with no clients and up to about 40 s with many; `stop_grace_period` is 60 s. Clean host reboots need the Docker daemon's `shutdown-timeout` to be at least 60 s. |
| Remove | `docker compose down` keeps the data volumes. **Never `down -v`**: it deletes all JetStream data. |
| Reload | `docker compose kill -s SIGHUP nats-1 nats-2 nats-3` applies accounts, users, permissions, TLS files, and most settings without restarting. |
| Rolling restart | Needed for listen addresses, `store_dir`, `sync_interval`, lame duck settings, ports, limits, and image changes: `scripts/rolling-restart.sh`. |

### Rolling restart and upgrade

```bash
./scripts/backup.sh && ./scripts/restore-drill.sh       # always have a tested backup first
# read https://docs.nats.io/release-notes/ for every version you cross, then:
echo 'NATS_IMAGE=nats:<new-version>-alpine3.22@sha256:<digest>' >> .env
./scripts/rolling-restart.sh                             # followers first, meta leader last
```

`rolling-restart.sh` handles one server at a time:

1. Require `check-cluster.sh` to exit 0.
2. Run `docker compose up -d --no-deps --force-recreate <server>`, which uses lame duck mode.
3. Wait for the container's health check.
4. Wait until the whole cluster is ready again, with every replica caught up.

It upgrades followers first and the meta leader last, as the NATS docs recommend.

**Never** change the image or a server setting and then run plain `docker compose up -d`: Compose
recreates all three servers at once and the cluster loses quorum.

Upgrade notes:

- **2.16 ack subjects.** 2.16 switches ack subjects to the v2 format; the permissions here already
  allow both.
- **Downgrades.** 2.15 can only be downgraded to 2.14.7 or newer
  ([2.15 upgrade guide](https://docs.nats.io/release-notes/upgrade-to-2.15)).
- **Persist the image.** Once all three servers run the new image, set it in `docker-compose.yaml` too
  (or keep it in `.env`), so a future `docker compose up` does not downgrade a server.

### Replacing a server

**Lost or corrupted volume.** Keep the same name and start with empty storage, one server at a time,
and only while the other two are healthy:

```bash
./scripts/check-cluster.sh                      # the other two must be OK
docker compose stop nats-3
docker compose rm -f nats-3 nats-3-init         # the init container also references the volume
docker volume rm nats_jetstream_3
docker compose up -d nats-3                     # init job chowns the fresh volume
./scripts/check-cluster.sh                      # wait until OK: replicas caught up from the peers
```

This was verified: the empty `nats-3` rejoined under the same peer identity and caught up the stream
(3,000 messages in 27 ms), and the cluster was fully ready within about 6 s. Rejoining as an empty peer
that resyncs over the network is the safer of the options the NATS docs give after a crash
([Replication and R3](https://docs.nats.io/learn/clustering/replication-and-r3)).

Rules for every replacement:

- **Never wipe two servers.**
- **Never copy one server's volume to another.**
- **Never rename a server that holds data.** `server_name` is its JetStream identity.

**Retiring a server for good,** for example when moving to new hosts:

1. Add the replacement as a fourth server.
2. Evacuate the old one: `nats server cluster evacuate <old>` (2.15). In a three-node cluster, R3
   streams have nowhere else to go, so add capacity first
   ([desired state and evacuation](https://docs.nats.io/learn/clustering/desired-state)).
3. Stop it.
4. Run `nats server cluster peer-remove <old>` with `sys-admin`. Running `peer-remove` against a
   server that is still running turns its JetStream off.

## 14. Backup and restore

**What and how.** `scripts/backup.sh` runs `nats backup account` as `app-admin` and writes every stream
with its consumer state to `backups/<UTC timestamp>/streams/<STREAM>/` (`backup.json`,
`stream.arc.s2`). This is NATS 2.15 backup v2 ([stream backup and restore](https://docs.nats.io/learn/backup-recovery/stream-backup-restore)):

- It runs online, without a stream lock, so publishing continues and each stream backup is a
  consistent point in time.
- Every stream directory is checked with `nats backup validate` right after it is written.
- A `MANIFEST.jsonl` next to `streams/` records the live stream and consumer positions. It stays
  outside `streams/` because `nats backup restore account` accepts only stream directories there.
- Local retention keeps the last `NATS_BACKUP_KEEP` backups (7 by default).

Schedule it with cron or launchd, for example `15 2 * * * /path/to/NATS/scripts/backup.sh`.

**Backup storage evaluation.**

| Target | Protects against | Not against |
|---|---|---|
| `NATS/backups/` (local) | Deleted or corrupted streams; bad publishes, which R3 replicates to all copies | Loss of the host or disk |
| SeaweedFS S3 (`seaweed-s3:8333`, this repo's object store since it replaced MinIO) or MinIO | Same, plus loss of the NATS volumes | Loss of the host: they run on the **same** Docker host |
| S3/SFTP on another machine, region, or provider | Host loss and site loss: the real DR copy | — |

Off-host copies use rclone. Set `NATS_BACKUP_REMOTE=remote:path` in `.env` and create
`secrets/rclone.conf` (0600). `backup.sh` then runs `rclone copy --immutable` followed by
`rclone check --one-way`. Example for a SeaweedFS S3 endpoint with a dedicated, bucket-scoped identity.
Do not reuse the admin keys from `SeaWeedFs/s3.json`.

```ini
[seaweed]
type = s3
provider = SeaweedFS
endpoint = http://seaweed-s3:8333        # better: an S3 endpoint on another host
access_key_id = <nats-backup access key>
secret_access_key = <nats-backup secret key>
```

The matching identity in SeaweedFS `s3.json` limits the actions to one bucket:

```json
{ "name": "nats-backup", "credentials": [{ "accessKey": "...", "secretKey": "..." }],
  "actions": ["Read:nats-backups", "Write:nats-backups", "List:nats-backups"] }
```

Create the bucket first. This path was tested against a throwaway SeaweedFS 4.35 with exactly this
identity layout.

**Restore drill: run it on a schedule.**

```bash
./scripts/restore-drill.sh                       # newest backup
./scripts/restore-drill.sh backups/20261106T020000Z
```

The drill never touches the cluster:

1. Start a throwaway single-node server from the same image on a new `--internal` network, with no
   ports.
2. Validate each stream archive.
3. Restore each stream as R1.
4. Compare messages and first and last sequence with the backup; check that every consumer is back
   with its ack floor (cross-checked against `MANIFEST.jsonl`).
5. Read the first and last message.
6. Remove everything.

Exit 0 means PASS. Rehearse at least quarterly, as the NATS
[disaster recovery guide](https://docs.nats.io/learn/backup-recovery/disaster-recovery) recommends.

**Real restores** run `nats backup restore ...` as `app-admin`. A restore recreates a stream; it never
merges into a live one, and the stream name cannot change.

| Scenario | Steps |
|---|---|
| A stream was deleted or corrupted | 1. Stop publishers. 2. If the stream still exists: `docker compose run --rm nats-box app-admin stream rm ORDERS -f`. 3. `docker compose run --rm nats-box app-admin backup restore stream /backups/<ts>/streams/ORDERS`. 4. Run `scripts/provision-jetstream.sh` and `scripts/check-cluster.sh`. |
| The whole cluster was lost | 1. Restore `certs/` and `secrets/` from their encrypted backup (or re-run `scripts/setup.sh` and redistribute credentials). 2. `docker compose up -d`. 3. Copy the backup into `backups/`. 4. `docker compose run --rm nats-box app-admin backup restore account /backups/<ts>/streams`. 5. `scripts/provision-jetstream.sh` (a no-op if the backup matches) and `scripts/check-cluster.sh`. |

Messages published after the backup are lost: that gap is your RPO.

## 15. Failure modes and recovery

| Event | Impact | What to do |
|---|---|---|
| One server crashes or is stopped | Leaders on it re-elect: about 1 s graceful, about 5 s on a crash, during which publishes to the affected streams time out. Clients reconnect to the others. Alert: `NatsServerDown`. | Restart it (`docker compose start nats-N`). It catches up automatically. Do not wipe it. |
| Two servers down | Quorum lost: R3 writes and consumer deliveries stop, admin changes are rejected. Data is safe. Alert: `NatsJetStreamQuorumLost`. | Bring either server back with its volume. Service resumes when two are up. |
| A server is gone for good while another is also down | No quorum and no way back for that server | Last resort, NATS ≥ 2.15: `docker compose run --rm nats-box sys-admin server cluster rescue`, then `server cluster peer-remove <dead>` ([disaster recovery](https://docs.nats.io/learn/backup-recovery/disaster-recovery)). Rescue can cause split brain if the dead server returns; destroy it first. |
| One volume corrupt or lost | That server cannot serve its replicas | Replace it with an empty volume (§13). |
| Disk or host lost | Everything | Rebuild and restore from the off-host backup (§14). |
| Storage full | Publishes fail on that server | `NatsJetStreamFileStorage*` alerts. Raise `NATS_JS_MAX_FILE` and the disk, or lower stream limits. |
| Bad publish or accidental delete | Replicated to all three copies | Restore from backup (§14). |

## 16. Moving to a real multi-host production deployment

| Area | Change |
|---|---|
| **Placement** | One NATS server per host, VM, or node, in **separate failure domains** (zone, rack, power feed, storage), or 5 servers for R5 critical state. Use `server_tags` (e.g. `az:a`) with `jetstream { unique_tag: "az:" }` so the replicas of a stream land in different domains ([jetstream config](https://docs.nats.io/reference/config/jetstream/)). |
| **Orchestration** | Either Compose on each host, running one server per host from the same config with its own `NATS_*` values, or Kubernetes with the official Helm chart (StatefulSet, PodDisruptionBudget `minAvailable: 2`, lame duck `preStop`). |
| **Networking** | Routes travel over a private network or VPN between hosts. Firewall 6222 to the cluster peers only, 4222 to client networks, and keep 8222 private to monitoring. The Docker aliases (`nats-N-cluster`) are replaced by real DNS names. |
| **Advertised addresses** | `cluster.advertise: <host-private-dns>:6222`, and route URLs use those names. Either keep `no_advertise: true` with explicit client lists, or set `client_advertise: <public-dns>:4222` on each server and drop `no_advertise` so clients discover peers. |
| **Certificates** | SANs = the real DNS names and IPs. Issue from an internal PKI (Vault, step-ca, cert-manager) with automated rotation, and keep the CA key off the servers. |
| **Persistent disks** | Local SSD/NVMe on each host (XFS/ext4), never NFS, NAS, or object storage. Set `max_file_store` to what the disk really holds, and alert on host disk space. |
| **Durability** | With independent failure domains, `sync_interval` can return to `2m`; keep `always` if every acknowledged message must survive a correlated power event. |
| **Operations** | NTP on every host. Off-site backups with restore drills. Per-host node-exporter metrics. Rolling upgrades host by host with the same health gates. |
